C1

A Work (Central folder + 1:1 Herdr workspace)Work (โฟลเดอร์กลาง + Herdr workspace แบบ 1:1) new patternรูปแบบใหม่

In one lineสรุปหนึ่งบรรทัดEvery task gets its own dedicated folder holding all repo worktrees and notes, paired 1-to-1 with its own Herdr workspace and tracked centrally by the Dispatcher.ทุกงานมีโฟลเดอร์เฉพาะของตัวเองที่รวม repo worktree และโน้ตทั้งหมดไว้ด้วยกัน คู่กับ Herdr workspace เฉพาะงานแบบ 1 ต่อ 1 และมีบันทึกกลางให้ Dispatcher เห็นทันที

Beforeก่อน
Branches, terminals, and notes for one task were scattered across separate repo folders and shared Herdr tabs.branch, เทอร์มินัล และโน้ตของงานเดียวกระจัดกระจายอยู่ตามโฟลเดอร์ repo ต่างๆ และปนกันใน Herdr tab เดียว
Nowตอนนี้
One slug maps to one work folder (<work-root>/<slug>/), one branch set across target repos, one dedicated Herdr workspace, and one central record in ~/.devbench/state/works/<slug>.json.1 slug แทน 1 โฟลเดอร์งาน (<work-root>/<slug>/), 1 ชุด branch ข้าม repo เป้าหมาย, 1 Herdr workspace เฉพาะ และ 1 บันทึกกลางใน ~/.devbench/state/works/<slug>.json
Why it mattersทำไมจึงสำคัญ
You can inspect, pause, resume, or archive an entire multi-repo effort as a single unit without risking collateral damage to other active tasks.สามารถตรวจสอบ พักงาน resume หรือ archive งานหลาย repo ทั้งก้อนได้ในคราวเดียวโดยไม่เสี่ยงกระทบงานอื่นที่กำลังรันอยู่

Think of it likeลองนึกถึง A dedicated project desk: every blueprint for that job sits on one table, logged on one central whiteboard, and when it finishes you box the whole desk at once.โต๊ะทำงานเฉพาะโปรเจกต์: แบบแปลนทุกแผ่นของงานนี้อยู่บนโต๊ะเดียว จดคุมไว้บนกระดานกลางใบเดียว และเมื่อจบงานก็เก็บลงกล่องทั้งโต๊ะในครั้งเดียว

A Work is the top-level lifecycle unit (creating -> active -> archiving -> archived). Inside <work-root>/<slug>/ live optional notes and one git worktree per involved repository, while its live state lives centrally at ~/.devbench/state/works/<slug>.json so the Dispatcher sees every work instantly. Archiving closes the 1:1 Herdr workspace first to release file locks, detaches clean worktrees while keeping git branches in their source repos, copies a frozen state snapshot into the folder, and moves it to the archive root.

Work คือหน่วยวงจรชีวิตระดับบนสุด (creating -> active -> archiving -> archived) ภายใน <work-root>/<slug>/ ประกอบด้วยโน้ตและ git worktree ของแต่ละ repo ขณะที่ live state เก็บไว้ที่ส่วนกลาง ~/.devbench/state/works/<slug>.json เพื่อให้ Dispatcher เห็นทุกงานทันที ตอน archive จะปิด Herdr workspace แบบ 1:1 ก่อนเพื่อปล่อยไฟล์ล็อก ถอด worktree ที่สะอาดโดยคง git branch ไว้ใน repo ต้นทาง คัดลอก frozen state snapshot ลงในโฟลเดอร์ แล้วจึงย้ายไปที่ archive root

New termsคำศัพท์ใหม่: work slug, central work folder, 1:1 Herdr workspace, work lifecyclework slug, central work folder, 1:1 Herdr workspace, work lifecycle

C2

4-Tier Agent Hierarchy & the 3 Session IDsลำดับชั้นเอเจนต์ 4 ระดับ และ Session ID 3 ชนิด new patternรูปแบบใหม่

In one lineสรุปหนึ่งบรรทัดWork flows cleanly down Dispatcher -> Owner -> (domain) worker -> decoupled sub-agent, and every persistent session tracks three distinct IDs so nothing gets lost.งานไหลลงตามลำดับ Dispatcher -> Owner -> (domain) worker -> sub-agent แยกอิสระ โดยทุก persistent session จะบันทึก ID แยก 3 ชนิดไว้ไม่ให้หลงทาง

Beforeก่อน
Every terminal looked identical; users had to remember which pane ran which role and lost native AI session IDs whenever a terminal closed.ทุกเทอร์มินัลหน้าตาเหมือนกันหมด ผู้ใช้ต้องจำเองว่า pane ไหนทำบทบาทอะไร และทำ native AI session ID หายทุกครั้งที่ปิดเทอร์มินัล
Nowตอนนี้
devbench manages persistent Owner and domain-worker sessions (leaving ephemeral sub-agents to the separate delegation layer) and saves each session's hc terminal ID, Herdr pane ID, and native AI session ID plus its cwd.devbench ดูแล Owner และ domain-worker session แบบคงอยู่ (แยก sub-agent ชั่วคราวไว้ใน delegation layer) และบันทึก hc terminal ID, Herdr pane ID และ native AI session ID พร้อม cwd ของแต่ละ session
Why it mattersทำไมจึงสำคัญ
Each ID has a different lifetime: when a Herdr pane or hc terminal disappears after a reboot, the saved native AI session ID and cwd let devbench resume the exact conversation.ID แต่ละชนิดมีอายุต่างกัน เมื่อ Herdr pane หรือ hc terminal หายหลังรีบูต ตัว native AI session ID และ cwd ที่บันทึกไว้จะช่วยให้ devbench resume บทสนทนาเดิมได้ตรงจุด

Think of it likeลองนึกถึง A hotel reservation: the room number (Herdr pane), keycard (hc terminal), and guest record (native AI session ID) are tracked separately so losing a keycard never erases the guest.การจองโรงแรม: เลขห้อง (Herdr pane), คีย์การ์ด (hc terminal) และประวัติแขก (native AI session ID) แยกเก็บกัน ทำให้ทำคีย์การ์ดหายก็ไม่เสียข้อมูลแขก

The Dispatcher creates the work and launches the Owner in the primary pane; the Owner coordinates optional domain workers (e.g. backend, frontend, docs) in tabs or splits inside the same 1:1 Herdr workspace. Ephemeral sub-agents stay outside devbench. Because Claude and Codex resume commands are cwd-scoped, state.json persists each session's exact cwd alongside capture status (auto, manual, pending, unavailable).

Dispatcher เป็นคนสร้างงานและเปิด Owner ใน pane หลัก ส่วน Owner ประสานงานกับ domain worker (เช่น backend, frontend, docs) ใน tab หรือ split ภายใน Herdr workspace 1:1 เดียวกัน ขณะที่ ephemeral sub-agent อยู่นอก devbench เนื่องจากคำสั่ง resume ของ Claude และ Codex ผูกกับ cwd ไฟล์ state.json จึงเก็บ cwd ของแต่ละ session คู่กับสถานะการเก็บ ID (auto, manual, pending, unavailable)

New termsคำศัพท์ใหม่: Dispatcher, Owner, domain worker, sub-agent, hc terminal ID, Herdr pane ID, native AI session IDDispatcher, Owner, domain worker, sub-agent, hc terminal ID, Herdr pane ID, native AI session ID

C3

Herdr Split: herdr-core Keeps Alive, herdr-app Showsการแบ่งหน้าที่ของ Herdr: herdr-core เลี้ยงโปรเซส, herdr-app แสดงผล existing boundaryขอบเขตเดิม

In one lineสรุปหนึ่งบรรทัดherdr-core (hc) keeps agent processes alive in the background while herdr-app only controls what you see in spaces, tabs, and panes.herdr-core (hc) คอยเลี้ยงโปรเซสเอเจนต์ให้ทำงานต่อเบื้องหลัง ส่วน herdr-app คุมเฉพาะสิ่งที่ผู้ใช้มองเห็นใน space, tab และ pane

Beforeก่อน
By default, hc kills every child terminal the moment its parent (the Dispatcher tab) closes or restarts, wiping out active Owners; meanwhile unlabeled hc terminals stay invisible in the Herdr window.โดยค่าเริ่มต้น hc จะฆ่า child terminal ทุกตัวทันทีที่ parent (แท็บ Dispatcher) ปิดหรือรีสตาร์ต ทำให้ Owner ที่กำลังทำงานอยู่ดับไปด้วย ส่วน hc terminal ที่ไม่มี label จะซ่อนอยู่ไม่โผล่ในหน้าต่าง Herdr
Nowตอนนี้
devbench creates the visible workspace via herdr-app space.new, then launches the agent via hc run --bg --outlive-parent with herdr.space=<id> — meaning it survives Dispatcher exit (NOT a zombie process: closing the pane/space or archiving still kills it cleanly) — and checks first_message.sent before reporting ready.devbench สร้าง workspace ที่มองเห็นด้วย herdr-app space.new แล้วเปิดเอเจนต์ด้วย hc run --bg --outlive-parent ติด label herdr.space=<id> ซึ่งแปลว่าอยู่รอดเมื่อ Dispatcher ปิด (ไม่ใช่ zombie process: การปิด pane/space หรือ archive ยังคงฆ่าโปรเซสและคืน RAM ตามปกติ) พร้อมเช็ก first_message.sent ก่อนรายงานว่าพร้อม
Why it mattersทำไมจึงสำคัญ
Separating an Owner's lifetime from the Dispatcher tab prevents accidental kills when you restart or close the Dispatcher, while pane close and archive still free memory cleanly — and checking first_message.sent prevents blind resends on trust prompts.การแยกอายุของ Owner ออกจากแท็บ Dispatcher ป้องกันไม่ให้งานที่ทำอยู่ดับตอนรีสตาร์ตหรือปิด Dispatcher ขณะที่การปิด pane และ archive ยังคงคืนหน่วยความจำอย่างสะอาด และเช็ก first_message.sent เพื่อไม่ให้ส่งข้อความซ้ำมั่วเมื่อติดหน้าต่างยืนยันสิทธิ์

Think of it likeลองนึกถึง A theater stage (herdr-app) vs backstage machinery (herdr-core): closing the curtain doesn't stop the engine running backstage, and switching off a room's pane or archiving shuts its engine down cleanly.เวทีโรงละคร (herdr-app) กับเครื่องจักรหลังเวที (herdr-core): การปิดม่านไม่ได้ดับเครื่องยนต์ที่ทำงานอยู่หลังเวที แต่การปิด pane ของห้องนั้นหรือ archive จะดับเครื่องยนต์ให้เรียบร้อย

In herdr-core, 'parent' refers to the Dispatcher terminal that spawned the session. Passing --outlive-parent only prevents active Owner/worker sessions from being killed when you close or restart the Dispatcher — it does not create zombie processes, because closing a pane/space in Herdr or running devbench archive explicitly kills and removes those terminals to free RAM and Windows file locks. Attaching herdr.space=<id> keeps them visible in the 1:1 workspace, and --no-daemon keeps Codex commands inside hc.

ใน herdr-core คำว่า 'parent' หมายถึงเทอร์มินัล Dispatcher ที่เป็นคนเปิด session การส่ง --outlive-parent มีไว้เพียงป้องกันไม่ให้ Owner/worker ที่กำลังทำงานอยู่ถูกฆ่าเมื่อคุณปิดหรือรีสตาร์ต Dispatcher เท่านั้น ไม่ได้ทำให้เกิด zombie process เพราะการปิด pane/space ใน Herdr หรือการรัน devbench archive จะ kill และลบ terminal เหล่านั้นออกเพื่อคืน RAM และปล่อยล็อกไฟล์บน Windows อย่างชัดเจน การติด label herdr.space=<id> ทำให้แสดงผลใน 1:1 workspace และ --no-daemon ทำให้คำสั่งของ Codex ทำงานอยู่ภายใน hc

New termsคำศัพท์ใหม่: herdr-core (hc), herdr-app, --outlive-parent, herdr.space label, first_message.sentherdr-core (hc), herdr-app, --outlive-parent, herdr.space label, first_message.sent

C4

Three Separated Stores & Live Reconciliation3 แหล่งเก็บข้อมูลที่แยกขาด และการ Reconcile กับความจริงสด new architectureสถาปัตยกรรมใหม่

In one lineสรุปหนึ่งบรรทัดPlugin code, external user config, and central Dispatcher work state live in three separate places — and Herdr is always treated as live truth over saved state.โค้ดปลั๊กอิน, external user config และ central work state ของ Dispatcher ถูกแยกเก็บเป็น 3 ส่วนชัดเจน โดยยึด Herdr เป็นความจริงสดเสมอ

Beforeก่อน
Personal paths, orchestration scripts, and ad-hoc notes lived together, so plugin updates risked wiping settings and stale files misled status checks.พาธส่วนตัว สคริปต์ประสานงาน และโน้ตต่างๆ ปนกัน ทำให้การอัปเดตปลั๊กอินเสี่ยงทับค่าตั้งค่า และไฟล์ state เก่าทำให้ดูสถานะผิดพลาด
Nowตอนนี้
Generic plugin code + config.example.json stay in the marketplace repo; personal config lives externally at ~/.devbench/config.json; work state lives centrally at ~/.devbench/state/works/<slug>.json so the Dispatcher reads all works instantly and reconciles against live hc/herdr-app.โค้ดปลั๊กอินที่เป็นกลาง + config.example.json อยู่ใน marketplace repo; user config อยู่ที่ ~/.devbench/config.json; work state อยู่ที่ส่วนกลาง ~/.devbench/state/works/<slug>.json เพื่อให้ Dispatcher อ่านทุกงานได้ทันทีและ reconcile กับ hc/herdr-app สด
Why it mattersทำไมจึงสำคัญ
Updating the plugin never clobbers personal paths or aliases, pushing code never leaks private paths, the Dispatcher sees every work in one place without scanning folders, and crashed operations recover cleanly from atomic phase checkpoints.อัปเดตปลั๊กอินได้โดยไม่ทับพาธหรือ alias ส่วนตัว push โค้ดได้โดยไม่หลุดข้อมูลเครื่อง Dispatcher เห็นทุกงานในจุดเดียวโดยไม่ต้องสแกนโฟลเดอร์ และกู้คืนงานที่สะดุดกลางทางได้จาก atomic phase checkpoint

Think of it likeลองนึกถึง A cookbook (plugin code), your pantry list (user config), and a central kitchen order board (work state) — updating the cookbook never erases your pantry or active orders.ตำราอาหาร (โค้ดปลั๊กอิน), รายการของในครัวคุณ (user config) และกระดานออเดอร์กลางในครัว (work state) — อัปเดตตำราใหม่ไม่ทำให้รายการของในครัวหรือออเดอร์ที่เปิดอยู่หาย

Plugin code (Rust binary + manifests) is read-only inside marketplace caches; user config carries schema_version and is checked against config.example.json without auto-overwriting; central work state lives at ~/.devbench/state/works/<slug>.json completely outside every git worktree, uses per-work locks and atomic renames, records operation phases for crash recovery, and drops a frozen snapshot into the archive folder on completion.

โค้ดปลั๊กอิน (Rust binary + manifest) เป็นแบบ read-only ใน marketplace cache; user config มี schema_version และตรวจเทียบกับ config.example.json โดยไม่เขียนทับอัตโนมัติ; central work state อยู่ที่ ~/.devbench/state/works/<slug>.json นอกทุก git worktree ใช้ per-work lock และ atomic rename บันทึก phase เพื่อกู้คืนเมื่อขัดข้อง และวาง frozen snapshot ในโฟลเดอร์ archive เมื่อจบงาน

New termsคำศัพท์ใหม่: plugin code, config template, user config, work state, live reconciliation, phase checkpointplugin code, config template, user config, work state, live reconciliation, phase checkpoint
